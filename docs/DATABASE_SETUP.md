# Database Setup & Operations Guide

## Overview

Synchrono AI Chatbot uses two distinct database systems:
1. **Internal PostgreSQL Database**: Stores user conversations, message history, and persistent LangGraph checkpoints. Initial table creation for application models (`Conversation`, `Message`) is handled at startup via SQLAlchemy ORM metadata (`create_all`), while LangGraph checkpoint tables are managed via dedicated saver setup methods. Incompatible existing legacy schemas do not auto-migrate and fail explicitly, requiring manual migration. Standalone legacy SQL scripts are **not** mounted.
2. **Analytics Database (StarRocks)**: Analytical data matching source-of-truth queried via MySQL wire protocol. The application accesses this engine using a dedicated read-only account (`synchrono_readonly`).

All container ports are bound strictly to loopback (`127.0.0.1`) to prevent external exposure.

## Environment Variables Contract

Configuration is managed via `.env` (canonical 10 database keys, no obsolete URI aliases or fallback chains):

```env
# Internal PostgreSQL (Conversation History & LangGraph Checkpoints)
INTERNAL_HOST=127.0.0.1
INTERNAL_PORT=5433
INTERNAL_USER=synchrono
INTERNAL_PASSWORD=<auto-generated-urlsafe-secret>
INTERNAL_DATABASE=synchrono_chatbot

# Analytics StarRocks (Read-Only Data Matching Source)
DB_HOST=127.0.0.1
DB_PORT=9030
DB_NAME=synchrono
DB_USER=synchrono_readonly
DB_PASSWORD=<auto-generated-urlsafe-secret>
```

> **Note on Deprecated Variables**: Obsolete variables `POSTGRES_URI` and `ANALYTICS_DB_URI` have been removed. Application configuration parses the canonical keys directly.

## Resource Requirements & Analytics Profile Gate

- **PostgreSQL**: Lightweight service (resource usage varies with workload). Runs on default profile.
- **StarRocks**: Requires **>= 4 GiB free RAM** to operate (runs combined Frontend and Backend JVM/native processes).
- **Default Behavior**: Running `docker compose up` starts **only** PostgreSQL. This protects memory-constrained host machines (~1.2 GiB RAM) from out-of-memory crashes.
- StarRocks is isolated under `--profile analytics`. Never start StarRocks unless host machine has >= 4 GiB free RAM.

## Operational Commands

### 1. Default Startup (Lightweight PostgreSQL Only)
Starts the internal PostgreSQL container for conversation and checkpoint persistence:
```bash
docker compose up -d
```

### 2. Verify Health and Status
Check running services and health status:
```bash
docker compose ps
docker compose logs -f postgres-chatbot
```

### 3. Start Analytics Services (StarRocks + Initializer)
*Prerequisite: Host has at least 4 GiB free RAM.*
```bash
docker compose --profile analytics up -d
```
The one-shot service `starrocks-init` waits for StarRocks health check, creates the database and `synchrono_readonly` user, updates the password idempotently, and grants read-only permissions (`SELECT ON ALL TABLES IN DATABASE`).

### 4. Start Full Stack (Databases + Application API)
```bash
docker compose --profile analytics --profile app up -d
```

### 5. Stopping Containers (Safe, Non-Destructive)
Stop services while preserving all data volumes:
```bash
docker compose --profile analytics --profile app stop
```
or
```bash
docker compose --profile analytics --profile app down
```

> ⚠️ **CRITICAL: NEVER RUN `docker compose down -v`**  
> Using `-v` permanently deletes named volumes (`synchrono_chatbot_data`, `synchrono_starrocks_fe_meta`, `synchrono_starrocks_be_storage`), destroying all conversation history, checkpoints, and analytics metadata.

## Important Architectural Notes

1. **Legacy SQL Script Incompatible & Schema Management**:  
   The file `scripts/init_chatbot_db.sql` is legacy and **not used or mounted**. SQLAlchemy ORM handles initial table creation (`create_all`) for application models on clean databases, and LangGraph checkpoint savers initialize their own checkpoint schema. Existing incompatible or legacy database tables do not automatically migrate; conflicting schemas fail explicitly and require manual migration.
2. **StarRocks Root Account Security Caveat**:  
   StarRocks official all-in-one image boots with an empty root password required by vendor bootstrap logic. This is strictly intended for local development. Network exposure is mitigated by loopback binding (`127.0.0.1`). The application connects using the unprivileged `synchrono_readonly` account.
3. **Idempotent StarRocks Provisioning**:  
   `scripts/init_starrocks.sh` uses POSIX-safe character validation and executes `CREATE USER IF NOT EXISTS`, `ALTER USER ... IDENTIFIED BY`, and `GRANT SELECT ON ALL TABLES IN DATABASE` via stdin to prevent credential exposure in process listings and safely sync updated passwords across restarts.
